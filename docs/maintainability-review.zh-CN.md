# 可维护性审查与重构方案

审查日期：2026-09-20  
状态：五阶段代码重构已实施；本地验收完成。云端性能验收经用户确认另行进行。

实施记录与维护约束见[可维护性重构实施记录](maintainability-implementation.zh-CN.md)。以下发现与基线保留为重构前的审查记录。

## 结论

项目已有较好的正确性保障：Hono RPC 类型推导、共享校验规则、独立导出模块，以及覆盖并发、事务回滚、计数器一致性和 D1 查询预算的测试。

维护压力主要集中在后端事务与路由耦合、前端异步生命周期保护不一致、详情页状态管理复杂，以及测试和样式的职责边界不清晰。建议保留现有技术栈，通过小步重构明确模块边界，优先处理事务和异步生命周期。

本方案的目标是降低修改成本与回归风险。路由、数据格式、事务语义和用户行为默认保持兼容；需要改变行为的事项应单独说明和验收。

## 审查范围与验证基线

本次检查覆盖：

- Worker 路由、认证、校验、数据库查询与写入、迁移及计数器维护。
- React 页面、组件、hooks、API 客户端、本地存储、国际化和导出。
- 样式组织、自动化测试、类型检查、构建和部署脚本。

验证结果：

| 检查 | 结果 |
| --- | --- |
| `npm run lint` | 通过，包括格式、TypeScript 和 ESLint 检查 |
| `npm test` | 23 个测试文件、243 项测试全部通过 |
| `npm run build` | Worker 与浏览器端生产构建通过 |

数据库测试最初因沙箱禁止本机监听而无法执行，获准启动本机模拟服务后全部通过。构建日志路径改到可写临时目录后再次验证通过。

上述结果是本次审查的时间点基线，不代表代码覆盖率或线上性能指标。本次未执行部署、远程迁移、线上压测、真实浏览器视觉验收或部署 dry run；未核实仓库之外的 CI 配置。以下未复现的行为风险均按静态审查发现描述。

## 应保留的设计

- API 请求与响应类型继续从 Hono 路由推导，保留类型负例测试，避免新增平行维护的 DTO。
- 权限归属、状态条件、容量限制继续在关键写入语句中检查，不能退化为仅在写入前查询。
- 明细写入和对应计数器更新继续在同一个 `DB.batch()` 中执行，并保持语句相邻。
- 保留独立聚合 SQL 对计数器的校验，不让测试完全依赖生产计数逻辑。
- 导出保留游标分页、读取上界、Web Worker 和批次确认机制。读取上界不等于完整数据库快照，状态仍按实际读取时的数据返回。
- 保留稳定错误码、前端翻译以及敏感信息不进入错误响应和日志的边界。
- 保留双语 README 同步更新规则。README 仍只包含项目概览、开发与部署内容，详细架构约束放在 `docs/`。

## 主要发现与建议

### 1. 高优先级：后端路由承担事务与数据访问职责

**证据**

[`src/worker/index.ts`](../src/worker/index.ts) 在审查时为 623 行，同时处理 HTTP、权限、业务规则、SQL、事务和结果转换。导入、核销、领取等操作的事务边界直接写在路由处理器中。

[`withCounterUpdate`](../src/worker/db/counters.ts) 已封装计数器更新，但调用方仍需正确匹配状态转换与明细写入，保持返回的两条语句相邻，并在同一个批处理中执行。核销导入还通过 `index % 5 === 1` 提取批处理结果，对语句布局存在隐含依赖。

**维护影响**

新增校验、状态转换或 SQL 时，需要同时理解 HTTP 行为、并发条件、计数器语义、结果位置和 D1 预算。仅按文件拆分路由不能消除这些风险。

**重构方向**

- 按认证、码池、兑换码、领取和导出拆分路由，路由负责输入校验、调用业务操作及构造响应。
- 将普通导入、核销导入、领取和删除封装成具体业务操作，由操作拥有完整事务及结果解释。
- 数据库模块提供具体查询和写入函数；多语句原子操作不能被通用 CRUD 抽象拆散。
- 将批处理布局和结果解码放在同一模块，用命名结果封装位置关系。
- 保留写入时的权限、容量和状态条件；模块抽取不能引入重复的权限查询或统计查询。

**D1 约束**

审查时，官方限制为免费方案每次 Worker 调用最多 50 次 D1 查询、付费方案 1000 次，每条查询最多 100 个绑定参数。批处理中的每条语句仍受限制约束。实施时应再次核对[官方限制](https://developers.cloudflare.com/d1/platform/limits/)。

现有预算测试位于 [`tests/api.test.mjs`](../tests/api.test.mjs)：

| 操作 | 当前基线 | 重构要求 |
| --- | --- | --- |
| 500 条普通导入 | 最多 39 次查询、单条语句最多 95 个参数 | 抽取模块不增加查询；保留参数预算测试 |
| 500 条混合状态核销 | 48 次查询、单条语句最多 62 个参数 | 保留预算余量，不额外增加数据库校验 |
| 计数器读取和关键排序查询 | 已有 `rows_read` 与索引相关测试 | 保留扫描量约束，并关注索引写入成本 |

普通导入按批提交，后续批次失败时，之前批次可能已成功；核销导入则整体在一个批处理中执行并回滚。这两种语义必须保留。`DB.batch()` 的事务行为参见 [D1 Database 文档](https://developers.cloudflare.com/d1/worker-api/d1-database/)。

### 2. 高优先级：请求生命周期保护不一致

**证据**

[`PoolDialogs.tsx`](../src/react-app/components/PoolDialogs.tsx) 中的 `useDialogRequest` 已提供同步请求锁、取消和生命周期检查；[`AuthDialog.tsx`](../src/react-app/components/AuthDialog.tsx) 的登录和 [`Claims.tsx`](../src/react-app/components/Claims.tsx) 的 Key 校验请求完成后直接调用 `onDone` 或 `onValidated`。

[`App.tsx`](../src/react-app/App.tsx) 的导航处理可以关闭弹窗。静态代码路径表明，导航卸载弹窗后，旧请求仍可能触发回调并影响导航或会话；本次未进行运行时复现，现有对应弹窗测试没有覆盖这一卸载场景。

**重构方向**

- 将 `useDialogRequest` 提取为独立 hook，统一需要生命周期保护的弹窗。
- 保留同步防重入机制，并明确成功、失败和结束回调在什么生命周期内有效。
- 补充请求中导航离开、卸载后成功响应、卸载后失败响应的回归测试。
- 领取操作单独保留成功结果的持久化职责。不能因为页面卸载而丢弃已经发出的兑换码。
- 请求取消不能视作服务端写入回滚；涉及 Cookie 和会话的操作还需明确导航后的会话同步策略。

### 3. 中高优先级：详情页状态管理复杂

**证据**

[`usePoolDetails.ts`](../src/react-app/hooks/usePoolDetails.ts) 同时管理分页、缓存、取消、请求序号、缓存代次、失败重试、码池状态写入和选择失效。React state 与多个 ref 共同维护状态一致性。

**维护影响**

增加交互时需要同时维护多个状态来源。将读取和写入简单拆成独立 hook，也可能失去当前共享的操作锁，重新引入旧响应覆盖新状态的问题。

**重构方向**

- 用 reducer 明确加载、成功、失败和失效等状态转换，减少需要同步更新的重复状态。
- 将查询键、缓存过期和容量淘汰抽成纯逻辑。
- 为列表读取和状态写入提供明确命名的操作，保留统一的生命周期与操作协调。
- 保留同步锁及已验证的旧响应隔离机制，逐步迁移，避免一次性重写。
- 保留切换码池、分页收缩、重试、缓存失效和旧列表响应覆盖状态等测试。

### 4. 中优先级：测试基础设施集中，静态检查范围不完整

**证据**

[`tests/api.test.mjs`](../tests/api.test.mjs) 在审查时为 2221 行，混合 D1 初始化、数据工厂、预算计量、故障注入和业务测试，并在文件内共享数据库。API 测试结束后会执行独立聚合校验，这是需要保留的保障。

[`eslint.config.js`](../eslint.config.js) 的主要规则覆盖 TS/TSX；复杂 `.mjs` 测试和维护脚本没有同等级的类型与 ESLint 检查。仓库内未见 CI workflow，但不能据此判断外部没有构建门禁。

**重构方向**

- 先抽出测试环境、迁移加载、数据工厂、D1 预算计量和故障注入工具，再按业务拆分测试。
- 明确每个套件的数据隔离与清理策略，避免直接拆文件后大量并行启动模拟服务。
- 优先将复杂辅助代码迁移到 TypeScript，并同步更新 Vitest 文件匹配规则和测试 tsconfig；其余脚本补齐适用的静态检查。
- 保留独立聚合校验、并发和回滚测试；预算计量仍覆盖整个请求，而非只计业务函数内部查询。
- 确认现有外部 CI 后，将必要检查设置为自动门禁，避免重复配置。

### 5. 中优先级：规则与环境类型存在重复维护入口

**证据**

导入上限 `500` 同时出现在 [`contracts.ts`](../src/shared/contracts.ts) 和 [`PoolDialogs.tsx`](../src/react-app/components/PoolDialogs.tsx)；状态、分页选项也存在多处表达。[`src/worker/types.ts`](../src/worker/types.ts) 的手写 `Bindings` 与 [`worker-configuration.d.ts`](../worker-configuration.d.ts) 的生成类型重复。

**重构方向**

- 集中业务上限、状态枚举和分页选项；文案通过参数引用适用的业务限制。
- D1 分批大小保留在数据库操作模块，与参数数目、语句数量及预算测试放在一起。
- 环境类型从 Wrangler 生成类型派生。对可能缺失的配置使用明确的类型收窄或派生类型，继续保留运行时失败关闭行为。
- 说明当前 `claimed` 汇总与当前处于 `claimed` 状态的数量之间的区别，减少统计语义误用。
- 保留 API 类型推导。拆分路由时通过链式组合导出完整类型，并使用已有类型测试验证兼容性，参见 [Hono RPC 文档](https://hono.dev/docs/guides/rpc)。

### 6. 中低优先级：样式文件之间存在交叉覆盖

**证据**

[`manager.css`](../src/react-app/styles/manager.css) 在审查时为 1127 行，覆盖列表、详情和记录表格；[`records.css`](../src/react-app/styles/records.css) 又覆盖详情页同名选择器。最终样式依赖 [`App.css`](../src/react-app/App.css) 中的导入顺序，颜色和间距仍有较多局部字面值。

**重构方向**

- 按列表、详情、记录表格和公共组件确定样式归属。
- 合并跨文件的重复规则及覆盖链，将同一组件的响应式调整与基础规则放在一起。
- 逐步统一颜色和间距变量；无需为本次整理更换样式技术栈。
- 使用桌面、移动端及中英文页面验证布局，重点检查长码池名、长兑换码、弹窗和表格滚动。

### 7. 中优先级：运行诊断与数据清理边界待完善

**证据**

[`index.ts`](../src/worker/index.ts) 的未知异常日志只包含请求方法和路径，虽然避免泄露敏感数据，但难以判断失败阶段。[`wrangler.jsonc`](../wrangler.jsonc) 已开启 observability，未显式开启 traces。

会话查询排除过期记录，但代码内未见过期会话清理入口；数据库已有 `sessions_expiry_idx`。导出最大数据量的线上性能和移动端内存验证也仍在 README 中列为待办。

**重构方向**

- 增加白名单化的操作名、错误分类、关联 ID 和耗时，不输出 SQL 参数、Cookie、Key、兑换码或备注。
- 配置适当采样的 tracing，参见 [Workers Traces 文档](https://developers.cloudflare.com/workers/observability/traces/)。
- 基于过期时间索引提供有批次上限的会话清理入口，限制每次执行的查询数和写入量，并记录执行结果。执行频率按实际增长量确定。
- 计数器全量校验和重建继续显式运行；重建要求暂停写入并等待在途请求结束，避免引入高频全表扫描。
- 在独立测试部署验证导出 CPU、D1 扫描量和移动端内存，再决定是否调整批次大小。

## 建议的职责边界

下表是目标职责，不要求为每一行机械创建独立抽象层。

| 区域 | 职责 | 约束 |
| --- | --- | --- |
| Worker 入口 | 中间件、路由组合、统一错误处理 | 保留完整 Hono RPC 类型推导 |
| 业务路由 | 校验输入、调用操作、返回 HTTP 响应 | 不直接编排复杂多语句事务 |
| 业务操作 | 导入、核销、领取、删除等完整操作 | 拥有事务、并发条件、预算与结果解码 |
| 数据库模块 | Schema、具体 SQL、计数器写入辅助 | 不在抽象内部偷偷增加查询 |
| 前端 hooks | 请求生命周期、操作协调、页面状态 | UI 回调与必须完成的持久化分别处理 |
| 前端组件 | 展示、表单交互、调用明确操作 | 拆分后保留可访问性与导航行为 |
| 共享模块 | 业务限制、校验、错误码、推导类型 | 业务规则与 D1 实现参数分别归属 |
| 测试辅助模块 | 环境、数据工厂、计量、故障注入 | 独立校验逻辑不依赖被测算法 |

## 分阶段实施计划

每个阶段可分成多个小 PR，避免同时移动文件、修改行为和调整数据库结构。

| 阶段 | 实施内容 | 验收标准 |
| --- | --- | --- |
| 1：建立保护边界 | 提取测试辅助工具；补齐弹窗生命周期保护 | 既有测试通过；卸载后旧响应不触发导航或旧 UI 回调；领取成功记录仍可保存 |
| 2：封装关键事务 | 抽取导入、核销、领取和删除操作；封装批处理结果 | 并发、回滚、部分提交语义不变；计数器独立校验通过；D1 查询和参数预算不增加 |
| 3：整理路由与规则 | 拆分 Hono 路由；集中业务限制；派生环境类型 | 路径、状态码和响应兼容；RPC 类型正反例通过；缺失配置仍按预期拒绝操作 |
| 4：整理前端状态 | 重构详情 reducer、缓存逻辑；拆分弹窗组件 | 缓存、重试、分页收缩、选择失效、导航及旧响应隔离行为不变 |
| 5：完善样式与运维 | 整理样式归属；完善诊断、清理入口与检查门禁 | 中英文响应式布局稳定；错误可定位且不泄露数据；维护操作有执行上限 |

建议首先实施阶段 1 和阶段 2。阶段 2 应先封装完整操作，再移动路由；阶段 4 则在异步生命周期保护统一后推进。

## 通用验收与回退原则

- 以现有行为测试和类型测试为基础，新增测试针对实际风险，不以固定测试数量代替验收。
- 每个变更运行与影响范围匹配的检查，阶段完成时运行 `npm run check`；该命令包含部署 dry run，不发布应用或执行远程迁移。
- 初期重构不要求数据库结构变化。如后续需要改变结构，新增迁移，不修改已应用的历史迁移，并单独评估 D1 读写量与部署顺序。
- 预算测试记录整个请求的查询数、参数上限及关键扫描量，防止鉴权或封装层的额外查询被遗漏。
- 文件移动与行为变更尽量分开提交，使回归可以定位并独立回退。
- 文档随实现更新阶段状态和验证结果；涉及 README 的变更同步维护英文与中文版本。

## 实施前仍需确认的事项

- 外部是否已有 CI 和部署门禁，以及当前实际使用的 Cloudflare 方案。
- 线上会话增长量、D1 使用量和导出最大数据量，用于确定清理及性能验收预算。
- 登录请求期间导航离开后的预期会话行为，尤其是服务端已经设置 Cookie 的场景。

这些事项不阻碍先开展测试辅助工具提取、现有生命周期保护复用和保持行为不变的事务封装。
